## Task brief · extension-stage

**Problem**

An application can't tell sqlate's migrator which Postgres extensions its schema needs. Today an
extension is either installed by hand or written into an ordinary migration with up and down
scripts. Those scripts pile up one per upgrade and have no honest down for a version that has no
downgrade script. The goal needs the migrator to reconcile each declared extension to the version
the image ships, ahead of every set and under the migrator's lock, so that starting replicas take
turns activating. A typed failure must come before any set runs, and `Verify` and a status report
must expose a mismatch, so go-database's admin service applies it unchanged.

**Behaviors**

1. `migrate.Options.Extensions` lists declarations in order. Each has a name and a removed flag,
   and no version. `New` refuses an empty or duplicate name. It also refuses any declarations
   when the dialect lacks the extension capability, and it still does no I/O.
2. The extension capability is a new migrate interface that returns statement text, as `Catalog`
   does. It returns:
   - a state query bound to the extension name, giving the installed version (none when not
     installed), the image's default version (none when the image doesn't offer the extension),
     and whether an update path runs from the installed version to the default;
   - the activation statements: create the extension if it doesn't exist, then update it to its
     default;
   - the removal statement: drop the extension if it exists, with RESTRICT.

   The dialect quotes the name.
3. `Up` checks every set's history and then the extensions. It checks every active declaration
   before activating any of them. If an extension isn't available in the image, the run fails
   with a typed error naming it. The run also fails if the installed version differs from the
   default and no update path leads to the default, which covers an installed version newer than
   the image's. That error names the extension and both versions. Either failure comes before any
   activation and before any set.
4. A declaration whose installed version already equals the default runs no statement, so a
   pre-installed database passes under an unprivileged role. A missing or older extension is
   activated, each declaration in its own transaction, in declared order, and each activation is
   logged.
5. A positive `Steps`, on the migrator or on a layer, runs the same check and activation after its
   existing refusals and before applying anything. It removes nothing.
6. After its sets, `Up` removes each removed declaration in declared order, each in its own
   transaction, logging each drop. If a dependent object is left behind, RESTRICT fails the run
   with the driver's error, mapped through the dialect. A removed declaration whose extension
   isn't installed, or isn't available, is a no-op.
7. Deleting a declaration only stops the migrator from managing it and never drops the extension.
   `Down`, `Reset`, and `Force` skip the stage, and `Reset` leaves extensions installed.
8. With `Unlocked`, the stage runs without the lock, as the sets do.
9. `Verify` checks extensions before sets, on the pool and without the lock. An active
   declaration that is missing or behind the default fails with a typed error that unwraps to
   `ErrPending`. So does a removed declaration that is still installed. An unavailable extension,
   or one with no update path, fails with its own class, not `ErrPending`. `Layer.Verify` and
   `Status` stay set-only.
10. `Migrator.Extensions(ctx)` reads each declaration's state in declared order, on the pool and
    without the lock. Each entry reports the name, the removed flag, the installed version, the
    image's default version, and whether the declaration is pending: missing or behind for an
    active declaration, still installed for a removed one. An unavailable extension shows an empty
    default version and is not an error.
11. Every typed error names the extension. `errors.Is` classifies it as `ErrExtensionUnavailable`,
    `ErrNoUpdatePath`, or `ErrPending`, and `errors.As` reaches the detail.
12. `postgres.Dialect` implements the capability:
    - the state query reads `pg_available_extensions` and `pg_extension_update_paths`;
    - activation is `CREATE EXTENSION IF NOT EXISTS` then `ALTER EXTENSION … UPDATE`;
    - removal is `DROP EXTENSION IF EXISTS … RESTRICT`.

    It references no new migrate symbol outside integration-tagged code, so the postgres module
    still builds against sqlate v0.7.0 when the workspace file is off.
13. `pgtest.MigratedWith(t, env, prefix, opts, sets...)` is `Migrated` with the caller's
    `migrate.Options`. `Migrated` becomes `MigratedWith` with empty options.
14. The live proofs use the integration image's contrib extensions:
    - hstore pre-installed at 1.4 makes `Verify` unwrap to `ErrPending` and `Extensions` report
      it pending; after `Up` it is at 1.8 and `Verify` passes;
    - a name the image lacks fails `Up` before any set and leaves no history row;
    - a removed hstore with a dependent column fails `Up`, and once a set migration drops the
      column the same `Up` drops hstore;
    - `Reset` leaves hstore installed;
    - two concurrent `Up` runs both succeed with one activation.
15. The unit tier, over the scripted driver, covers what the image can't stage: an installed
    version newer than the default with no update path fails before any activation and before
    any set.
16. The guide documents the stage, `Extensions`, the new errors, the capability, and
    `MigratedWith`. The base changelog records v0.8.0, and postgres's changelog records its
    additions under Unreleased.

**Test seams**
- `migrate.Migrator` over the scripted `database/sql` driver, with a test dialect that implements
  the extension capability (behaviors 1–11 and 15).
- `pgtest.MigratedWith` and `migrate.Migrator` against the integration PostgreSQL, under the
  integration tag and the committed workspace (behaviors 12–14).

**Slices**
1. Upgrade sqlate: marathon (claude-plugins) 0.22.0 → 0.24.0 and jdx/mise-action v5.2.10 →
   v5.3.0. Done when `mise run currency` exits 0 and the check passes.
2. Declarations and the capability: the `Options.Extensions` declaration, `New`'s validation, the
   capability interface, the extension error classes, and `Migrator.Extensions` reporting, with
   unit tests and the guide.
3. Activation in `Up` and positive `Steps`: check-all-then-activate, the failures before any
   activation or set, one transaction per activation, logging, and `Unlocked`. Includes the
   newer-than-image unit case and the guide.
4. `Verify` reports extensions before sets: pending activation and pending removal unwrap to
   `ErrPending`, and unavailable or no-path fail as their own classes. Unit tests and the guide.
5. Removal at the end of `Up`, with `Down`, `Reset`, and `Force` skipping the stage. Unit tests
   and the guide.
6. postgres: the capability's statements with unit tests of their text, `pgtest.MigratedWith`,
   the live proofs in behavior 14, the postgres changelog under Unreleased, the base changelog's
   v0.8.0 entry, and the guide.

**Out of scope**

- No extension version declared in Go, no history table, no schema option: an extension installs
  where the session's default schema puts it.
- No `CASCADE` on create or drop, and no drop when a declaration is deleted.
- Shipped sets declaring extensions.
- pgvector, its module, the canonical image's pgvector build and its currency line, sqlint's
  `extensions` key, and go-database's `admin.Status` field.
- Moving postgres onto v0.8.0 and releasing `postgres/v0.9.0`, which sqlint-extensions does.

**Door**

One-way for the `v0.8.0` tag: once pushed, migrate's new exported API is public at that version
(the `Options.Extensions` declaration, the capability interface, `Migrator.Extensions`, and the
error classes). Everything else stays two-way until `postgres/v0.9.0`: postgres's capability
methods and `pgtest.MigratedWith` merge unreleased, and so do the tests and the guide.

**Release**

`v0.8.0`

## Decisions

- plan: The image is an extension's sole version source: `postgres:19.0-alpine` with each extension
  built from source, pgvector pinned by `ARG PGVECTOR_VERSION`. Rejected: pgvector/pgvector's
  Debian images, PGDG on Debian, and a version declared in Go.
- plan: Declarations live in `migrate.Options.Extensions` (name, optional removed state, no
  version); the stage runs before every set under the migrator's lock, each in its own transaction,
  in declared order. Rejected: an application-owned bottom set of up/down migrations.
- plan: The stage reconciles against `pg_available_extensions` with no history table; a mismatch
  makes `Verify` unwrap to `ErrPending`; an unavailable version, or an installed one newer than the
  image's with no path down, fails before any set runs.
- plan: A removed declaration runs `DROP EXTENSION IF EXISTS x RESTRICT` after the sets; deleting a
  declaration never drops; Reset leaves extensions installed.
- plan: Shipped migration sets declare no extensions; only the application does.
- plan: sqlint's `extensions` key; a listed module exports forms, or `forms = []` with a `reason`,
  or is refused. No sqlint check against `Options.Extensions`.
- plan: Module paths `sqlate/postgres/pgvector` and `go-database/postgres/pgvector`; the latter uses
  pgvector-go's root module over `database/sql` and depends on the former's metric table.
- extension-stage: Extension statements come from a migrate dialect capability returning statement
  text (state query, activation, removal), implemented by `postgres.Dialect`; declarations are
  data. Rejected: check and activation functions carried on each declaration.
- extension-stage: Activation runs before any apply (`Up` and positive `Steps`); removal runs only
  at the end of `Up`; `Down`, `Reset`, and `Force` skip the stage.
- extension-stage: The check uses `pg_extension_update_paths`, so an installed version with no
  path to the image's default fails as `ErrNoUpdatePath`, which covers an installed version newer
  than the image's; an unavailable extension fails as `ErrExtensionUnavailable`.
- extension-stage: A removed declaration still installed is pending: `Verify` unwraps to
  `ErrPending` and `Extensions` marks it pending, so `admin.Status` reports it not `Ready`.
- extension-stage: Releases `v0.8.0` alone. postgres's capability and `pgtest.MigratedWith` merge
  unreleased against v0.7.0; sqlint-extensions' upgrade slice moves postgres onto v0.8.0 and
  releases `postgres/v0.9.0` before pgvector-sql needs it.
