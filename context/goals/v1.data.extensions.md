## Task brief · sqlint-extensions

**Problem**

sqlint keeps native forms out of standard-tier files only for the configured engine. When a module
uses a Postgres extension such as pgvector, nothing stops that extension's operators, types or
functions from appearing in a standard-tier file, so the file passes as portable when it isn't.
The goal needs an `extensions` key whose listed modules add their native forms to the engine's deny
list. A listed module must either declare its forms or give a reason why it has none; otherwise it
is refused. pgvector-sql then builds the first such module, and it needs postgres's extension
capability and `pgtest.MigratedWith` released, built against sqlate v0.8.0.

**Behaviors**

1. A module's `sqlint.toml` accepts a top-level `extensions` list of strings. `Load` refuses each of
   these, one error line each, beginning `sqlint.toml:`:
   - a value that isn't a list of strings;
   - an empty entry;
   - a repeated entry;
   - any `extensions` while `engine` is unset.
2. `Load` accepts `[export] reason`, a string, beside `[export.native_forms]`. It also tells a
   `native_forms` table declared empty apart from an absent one. So an extension module's own file,
   with `native_forms = {}` and a `reason`, loads clean.
3. Each entry is found the way `engine` is. When its first segment contains a dot it is a module
   path, resolved through the `Resolver` to the version go.mod pins, workspace and replace included.
   Otherwise it is a directory of the tree. An entry that doesn't resolve, or that has no
   `sqlint.toml`, is a finding against `sqlint.toml` naming `extensions` and the entry, the way a
   failed engine lookup is reported today. The rest of the tree is still linted.
4. A listed module is accepted when its export has at least one native form, or an empty
   `native_forms` table beside a non-empty `reason`. Anything else is refused, including a missing
   table or an empty table with no reason. A refusal is a finding against `sqlint.toml` that names
   the entry and says it exports neither native forms nor a reason. A refused module adds no forms,
   and the rest of the tree is still linted.
5. An accepted module's forms join the engine's deny list. They are matched exactly where the
   engine's are:
   - in standard-tier files only;
   - in roles whose `native_forms` switch is on, overrides included;
   - against code with literals, quoted identifiers and comments stripped.

   Native-tier files are never checked against them. A form whose expression doesn't compile is a
   finding against `sqlint.toml` naming the entry and the form, and the module's other forms still
   apply.
6. A finding from an extension's form names the listed entry beside the form's name. For example:
   `"<=>" (cosine_distance, from <entry>) in a standard-tier file; declare the tier native and name
   the port`. The same form name may appear in the engine and in several extensions. Findings from
   the engine's forms are unchanged.
7. sqlint never reads the `native:` header. It stays free text, and the guide documents the
   convention that a native file using an extension names that extension there
   (`native: postgres, pgvector — <=> cosine distance`).
8. postgres and sqlint require sqlate v0.8.0. Each builds, tests and lints with the workspace off.
9. The guide's sqlint section documents:
   - the `extensions` key and how entries are found;
   - an extension module's export: forms, or an empty table with a `reason`;
   - the `Load` refusals and the findings against `sqlint.toml`;
   - the extension finding's message;
   - the `native:` header convention;
   - that review keeps the `extensions` list in step with `migrate.Options.Extensions`, since
     sqlint can't read Go values.
10. sqlint's changelog records the key and the v0.8.0 requirement under Unreleased. postgres's
    changelog records `v0.9.0`: the additions now under Unreleased, plus the v0.8.0 requirement.

**Test seams**
- `sqlint.Load` over configuration text (behaviors 1–2).
- `sqlint.Lint` over `fstest.MapFS` fixture trees. Extension modules are fixtures, found either as
  directories of the tree or through a stub `Resolver` keyed by module path (behaviors 3–6). No
  pgvector module is needed.

**Slices**
1. Upgrade sqlate: postgres and sqlint move from sqlate v0.7.0 to v0.8.0. postgres's changelog gets
   its `v0.9.0` entry and sqlint's gets the requirement under Unreleased. Done when a fresh
   `mise run currency` exits 0 (rerun it, since the Go proxy's version list lags new tags) and the
   check passes.
2. The `extensions` key in `Load`: the list, its refusals, `extensions` without `engine`, and
   `[export] reason` with an empty `native_forms` table. Unit tests, and the guide's configuration
   block and prose.
3. Lookup and the deny list in `Lint`:
   - entries found as module paths or directories;
   - lookup failures and refused modules reported against `sqlint.toml`;
   - accepted forms joining the deny list in standard-tier files only;
   - bad expressions reported;
   - the finding naming the entry.

   Unit tests over fixture modules, the guide's checks and the `native:` header convention, and
   sqlint's changelog under Unreleased.

**Out of scope**

- The `sqlate/postgres/pgvector` module, its forms, and any `extensions` entry in sqlate's own
  configuration. pgvector-sql does these.
- Checking `extensions` against `migrate.Options.Extensions`.
- Enforcing extension names in the `native:` header.
- Requiring an engine to export native forms. An engine with none still yields an empty list.
- Releasing sqlint, and stripping dollar-quoted bodies before matching.

**Door**

One-way for the `postgres/v0.9.0` tag. Once it is pushed, postgres's `ExtensionCatalog` methods
and `pgtest.MigratedWith` are public at that version, requiring sqlate v0.8.0. sqlint's
`extensions` key, the export's `reason`, and the finding format merge unreleased. They stay two-way
until pgvector-sql releases sqlint.

**Release**

`postgres/v0.9.0`

## Decisions

- plan: The image is an extension's sole version source: `postgres:19.0-alpine` with each extension
  built from source, pgvector pinned by `ARG PGVECTOR_VERSION`. Rejected: pgvector/pgvector's
  Debian images, PGDG on Debian, and a version declared in Go.
- plan: Shipped migration sets declare no extensions; only the application does.
- plan: Module paths `sqlate/postgres/pgvector` and `go-database/postgres/pgvector`; the latter uses
  pgvector-go's root module over `database/sql` and depends on the former's metric table.
- extension-stage: A removed declaration still installed is pending: `Verify` unwraps to
  `ErrPending` and `Extensions` marks it pending, so `admin.Status` reports it not `Ready`.
- sqlint-extensions: sqlint stays unreleased; pgvector-sql's Release line adds `sqlint/v0.5.0`
  once pgvector's real forms have exercised the key.
- sqlint-extensions: rejected sqlfluff and squawk, which lint against a fixed dialect and can't
  read a module's exported deny list.
