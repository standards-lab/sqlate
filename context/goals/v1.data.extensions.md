## Task brief · principles

**Problem**

The strategy for Postgres extensions sits in a coordinator note, and the note trails the merged
code in four places. sqlate's and go-database's merged code already expresses the strategy. Until
it is an architecture page, review can't cite it, and the two repositories' standards files can't
point to it.

Promoting it extends rolling currency to the pin of a source a Dockerfile builds. Neither
repository's upgrade meets rolling currency today:
- it moves only the mise pins and the Go modules, and runs the Go modules first;
- it moves no workflow action pin, no compose `FROM` line, and no source ARG;
- it reads no hold list;
- sqlate's guide says a maintainer raises the pgvector ARG by hand.

**Behaviors**

1. go-database's `postgres` module requires go-database v0.13.0, with an Unreleased changelog
   entry, and go-database's currency reports nothing trailing.
2. sqlate's currency script takes one mode, `report` or `upgrade`. `mise run currency` runs
   `report` and `mise run upgrade` runs `upgrade`. The two modes use the same scans, so upgrade
   moves exactly what report lists.
3. `upgrade` moves every pin `report` lists as trailing, in rolling currency's order:
   1. the mise pins;
   2. each module's `go` directive (to the current Go minor, with no toolchain line), its direct
      requirements, and a tidy;
   3. each workflow's action pins;
   4. each compose Dockerfile's `FROM` tag;
   5. each `ARG <NAME>_VERSION` whose `ADD` fetches a GitHub repository at `v${<NAME>_VERSION}`.

   It prints one `upgrade:` line for each pin it moves, and on a current tree it changes nothing.
4. A `HOLDS` list in mise.toml's `[env]` holds pins, one `<item> <pin>: <reason>` line each, with
   the item named as `report` names it, as in docproc. It ships empty.
   - `report` shows a held pin as `held:` with its reason, and doesn't count it as trailing.
   - `report` exits 0 when every pin it lists is held.
   - `upgrade` skips a held pin.
5. sqlate's guide describes both modes, what `upgrade` moves, and `HOLDS`, and no longer says the
   ARG is raised by hand. The README's task lines match.
6. go-database's currency script is byte-identical to sqlate's. Its tasks, its empty `HOLDS`, and
   its README task lines are wired the same way, so behaviors 2–4 hold in go-database.
7. sqlate's standards file points to the Go Elemental "Database extensions" principle. Its scope
   line names `migrate`'s extension declarations, `postgres`'s extension statements, the
   `postgres/pgvector` sub-module, and the compose Dockerfile.
8. go-database's standards file points to the same page. Its scope line names `admin`'s extension
   status and readiness, the `postgres/pgvector` sub-module, and the compose Dockerfile.
9. A new Go Elemental principle, "Database extensions" (level `go-elemental`), is listed in both
   Go Elemental indexes and states four rules:
   - (a) An extension's features are native tier, and only the packages that may import a provider
     use them.
   - (b) The image is the version. Each extension is built from source onto the engine's one
     baseline image and pinned once in the Dockerfile, and no code declares its version.
   - (c) The application declares extensions by name only. The migrator reconciles them against
     the engine's catalog ahead of every migration set, with no history table:
     - it fails before any set when an extension is unavailable or has no update path;
     - it drops an extension only when the extension is declared removed;
     - readiness is false on any mismatch.
   - (d) An extension's SQL layer is a sub-module of the SQL library, and its Go layer a sub-module
     of the infrastructure library. The engine module never requires its extensions, and each
     extension module proves itself in its own integration tier.

   The page asserts no repository's version or state, and may link sqlate's examples pinned at a
   tag. It leaves out build flags, catalog names, metric tables, sqlint config syntax, typed
   errors, status fields, index recipes, client-library usage, and the shipper rule.
10. "DSL-driven services" extends its native-forms bullet: the linter also refuses a declared
    extension's native forms in a standard-tier file, and a native file's header names the
    extension it uses.
11. "Rolling currency" lists, among the versions it covers, each source a Dockerfile builds,
    pinned by one build argument. "Releases and CI" adds it to what currency reports and upgrade
    moves.
12. The architecture check passes, and so does `mise run check` in sqlate and in go-database.

**Test seams**
- Each repository's `mise run currency` and `mise run upgrade`, run against pins lowered by hand
  and against a `HOLDS` entry (behaviors 1–4 and 6).
- The architecture check (links, front matter, `lint-context`, `lint-references`), plus a read for
  coherence and for rule-only claims (behaviors 9–11).

**Slices**
1. go-database upgrade: `postgres` requires go-database v0.13.0, with the Unreleased entry. Done
   when go-database's currency exits 0 and its check passes.
2. sqlate's upgrade mode and pointer: the two-mode script with `HOLDS`, the rewired tasks, the
   guide and README, and the standards pointer. Done when:
   - `upgrade` on the current tree leaves no diff;
   - with an action pin, the compose `FROM` tag, and `PGVECTOR_VERSION` lowered by hand, `report`
     lists all three and exits 1, then `upgrade` restores them and `report` exits 0;
   - with the ARG lowered and a `HOLDS` line naming it, `upgrade` leaves the ARG, and `report`
     shows it held and exits 0;
   - the check passes.
3. go-database's copy and pointer: the copied script, its wiring and `HOLDS`, the README, and the
   standards pointer. Done when slice 2's demonstrations pass in go-database, the script matches
   sqlate's byte for byte, and the check passes.
4. The architecture pages: "Database extensions" with its two index entries, the "DSL-driven
   services" clause, and source-ARG coverage in "Rolling currency" and "Releases and CI". Done
   when the architecture check passes and the pages read as rules only.

**Out of scope**
- Pointers in any other repository.
- From docproc's script, everything sqlate and go-database have no use for: image pins in Go
  source, tool modules, and per-tool upgrades.
- Changes to CI, including running currency there.
- Any Go code change, release, or tag.
- The shipper rule on a page.

**Door**

Two-way. Docs, scripts, and task wiring in three repositories, with no tag.

## Decisions

- sqlint-extensions: rejected sqlfluff and squawk, which lint against a fixed dialect and can't
  read a module's exported deny list.
- pgvector-go: rejected `Param`/`Dest` wrappers over `[]float32`, which the import rule already
  makes unnecessary, and a `migrate.Extension` helper in go-database's `postgres/pgvector`.
- principles: the extension rules move from Go Elemental to the architecture level once a second
  standard's code expresses them.
- principles: go-database's `scripts/currency.sh` is a byte-for-byte copy of sqlate's. Rejected:
  keeping the inline upgrade task in `mise.toml`.
