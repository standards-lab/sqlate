## Task brief · pgvector-sql

**Problem**

The extension stage and sqlint's `extensions` key exist, but no extension module uses them yet.
pgvector, the first case, needs four things:

- a module that names its native forms, its catalog name and its metrics;
- an image that builds it from source, with a pin that currency watches;
- live proof against that image that the stage manages it and that the per-space partial HNSW
  index works;
- a real export that sqlint's key resolves, so that sqlint can be released.

pgvector-go then builds on this module's released metric table.

**Behaviors**

1. A new module, `github.com/standards-lab/sqlate/postgres/pgvector`, with its own `go.mod`,
   changelog and `doc.go`. Its package names:
   - the extension's catalog name, `vector`;
   - the metrics `l2`, `cosine` and `inner product`, mapped to the operators `<->`, `<=>` and `<#>`
     and to the opclasses `vector_l2_ops`, `vector_cosine_ops` and `vector_ip_ops`.

   The table covers the `vector` type only and has no distance-function field. The package imports
   only the standard library.
2. The module's `sqlint.toml` exports `[export.native_forms]`. Each form is named after pgvector's
   own name, so a finding reads `"<=>" (cosine_distance, from <entry>)`. The forms are:
   - the six distance operators, each named for its function: `<->` l2_distance, `<#>`
     negative_inner_product, `<=>` cosine_distance, `<+>` l1_distance, `<~>` hamming_distance and
     `<%>` jaccard_distance;
   - `vector` only where a type goes (`AS vector`, `vector(`), and `halfvec` and `sparsevec` as bare
     words;
   - the index methods `hnsw` and `ivfflat` after `USING`;
   - the callable functions `l2_distance`, `inner_product`, `cosine_distance`, `l1_distance`,
     `hamming_distance`, `jaccard_distance`, `vector_dims`, `vector_norm`, `l2_norm`,
     `l2_normalize`, `binary_quantize`, `subvector`, `array_to_vector`, `array_to_halfvec` and
     `array_to_sparsevec`, each followed by `(`;
   - the `hnsw.*` and `ivfflat.*` settings.

   No form matches an unquoted identifier named `vector`, and none matches a portable statement.
3. sqlate's root `sqlint.toml` lists the module under `extensions`, and the root check resolves it
   through the committed go.work. The check fails if the module's export is refused or a form
   doesn't compile.
4. The compose image is still `FROM postgres:19.0-alpine`. On top of it, the image builds pgvector
   from source:
   - the version is `ARG PGVECTOR_VERSION`, with a default of the latest tag (0.8.7);
   - the source is fetched by `ADD` from pgvector's git repository at `v${PGVECTOR_VERSION}`;
   - both `make` and `make install` run with `with_llvm=no`, and `make` also runs with
     `OPTFLAGS=""`;
   - the build tools are removed in the same layer.

   `pg_available_extensions` then offers `vector` at that version, and the HEALTHCHECK, user and
   database are unchanged.
5. Currency also reads Dockerfile ARGs. In each compose Dockerfile, an `ARG <NAME>_VERSION=<v>`
   whose `ADD` line names a GitHub `.git#v${<NAME>_VERSION}` URL is compared with that
   repository's highest semver tag, read from tags rather than releases. A trailing ARG is
   reported as `<dockerfile>: <owner>/<repo> <v> -> <latest>`, and currency exits non-zero. Other
   ARGs are ignored, and a failed lookup fails currency.
6. The module's integration tier, behind the `integration` tag and using `SQLATE_DSN` and
   `pgtest`, proves the stage against the image:
   - `MigratedWith` and a declaration of `vector` install it at the image's default;
   - `Extensions` reports it installed at the default and not pending, and `Verify` passes;
   - a removal is refused while a `vector` column depends on the extension, and succeeds once a set
     migration drops the column.
7. The same tier proves the per-space recipe on one untyped `vector` column, with a partial HNSW
   index per space over a typed cast (`(embedding::vector(n)) <opclass>`, `WHERE space = <id>`):
   - a query that repeats the cast and the space predicate plans an index scan on its space's
     index;
   - the same query without the cast doesn't use the index;
   - an insert of the wrong dimension into an indexed space fails.

   The tier uses enough rows, or a planner setting, that the plan assertion is deterministic, and
   every metric in the metric table is exercised through its opclass and operator.
8. `mise run integration` runs the integration tier of both `postgres` and the new module, and
   `mise run acceptance` covers both. The check, build, tidy, test and lint tasks include the new
   module, and go.work uses it.
9. The guide documents:
   - the module: the extension name, the metric table, its forms, and why the root config lists it
     although no `Options.Extensions` declares it (a test-only listing);
   - the canonical Dockerfile, with its pin and build flags, and that a consumer copies it;
   - the currency ARG check;
   - the per-space recipe, its repeated cast and its dimension check;
   - that the integration tier now covers two modules.
10. The new module's changelog records `v0.1.0`. sqlint's changelog turns Unreleased into `v0.5.0`.

**Test seams**
- The module's unit tests: the metric table, and each form, parsed from the module's own
  `sqlint.toml` with BurntSushi/toml, matched against a positive and a portable sample
  (behaviors 1–2).
- The root check's sqlint run under go.work (behavior 3).
- `mise run currency` against the Dockerfile (behavior 5).
- `pgtest.MigratedWith` and `migrate.Migrator` in the module's integration tier, through
  `mise run acceptance` (behaviors 4, 6 and 7).

**Slices**
1. The module, its export and the root listing.
   - The package, with the extension name and the metric table.
   - The `sqlint.toml` forms, with unit tests.
   - go.work, the module list in the mise tasks, and the root `extensions` entry.
   - The guide's module and forms prose, and the changelog entries for the module and sqlint.

   Done when the check passes with the module listed.
2. The image and its currency.
   - The Dockerfile builds pgvector 0.8.7 from source.
   - currency.sh gains the generic ARG check.
   - The guide's Dockerfile and currency prose.

   Done when `mise run db:up` offers `vector` 0.8.7, currency exits 0, and lowering the ARG default
   by hand makes currency report pgvector trailing.
3. The live proof.
   - The module's integration tier proves the stage and the per-space recipe; its `go.mod` requires
     `postgres` v0.9.0.
   - `mise run integration` runs both modules.
   - The guide's recipe and integration prose.

   Done when `mise run acceptance` passes and the check passes.

**Out of scope**

- go-database's helpers, compose stack and integration tier (pgvector-go).
- `halfvec`, `sparsevec`, `bit` and `l1` in the metric table, and any distance function or score
  conversion in the API.
- Forms for vector arithmetic and for `avg` and `sum` over vectors, which no expression can tell
  apart from core SQL.
- Upgrading the ARG in `mise run upgrade`, as with the `FROM` line.
- An integration job in CI. Vetting and linting the integration suites under their tag.
- Releasing `postgres` or the base module, neither of which changes.

**Door**

One-way for both tags. Once `sqlint/v0.5.0` is pushed, the `extensions` key, `[export] reason`
and the extension finding format are public. Once `postgres/pgvector/v0.1.0` is pushed, the
extension name, the metric table and the exported forms are public. The Dockerfile, the currency
check and the tests stay two-way.

**Release**

`sqlint/v0.5.0`, `postgres/pgvector/v0.1.0`

## Decisions

- plan: The image is an extension's sole version source: `postgres:19.0-alpine` with each extension
  built from source, pgvector pinned by `ARG PGVECTOR_VERSION`. Rejected: pgvector/pgvector's
  Debian images, PGDG on Debian, and a version declared in Go.
- plan: Shipped migration sets declare no extensions; only the application does.
- plan: go-database's module is `go-database/postgres/pgvector`. It uses pgvector-go's root module
  over `database/sql` and depends on `sqlate/postgres/pgvector`'s metric table.
- extension-stage: A removed declaration still installed is pending: `Verify` unwraps to
  `ErrPending` and `Extensions` marks it pending, so `admin.Status` reports it not `Ready`.
- sqlint-extensions: rejected sqlfluff and squawk, which lint against a fixed dialect and can't
  read a module's exported deny list.
- pgvector-sql: go-database copies sqlate's canonical `compose/postgres/Dockerfile` and the ARG
  check in `scripts/currency.sh`.
- pgvector-sql: an extension module's live proof runs in its own module's integration tier, with
  that module requiring `postgres` for `pgtest`. The engine module never requires its extensions.
